# Yive 长期路线图

## 总目标

把 Yive 从“局域网/服务器网页工具”推进成“手机 App 控制本地电脑 Agent 的远程开发平台”。

长期形态应该是：

```text
手机 App / PWA
    -> 云端 Relay 中转服务
        -> 用户自己的电脑 Yive runtime
            -> 本地 PTY Agent
            -> 本地工作区文件
```

核心原则是：Agent、PTY、源码、工作区和 API Key 默认留在用户自己的电脑上；服务器主要负责公网转发、配对、鉴权、设备管理和临时文件传输。

## 当前方向

当前代码已经在往这个方向推进：

- `/mobile` 已经是手机端入口。
- Relay 已经支持手机和电脑配对。
- 本地电脑 runtime 可以主动连接 Relay。
- 手机可以通过 Relay 访问 workspace、agent、actions 和 terminal WebSocket。
- 原始终端优先采用“手机显式接管”的方式解决窄屏显示问题。
- 设备 token 可以持久化，也可以撤销。
- PWA manifest 已经指向手机远程控制入口。
- PWA manifest 已经包含手机和桌面两种安装截图。
- 手机端已经支持 Chromium 安装提示和 iOS/Safari 手动添加到主屏幕提示。
- 手机 Relay 直连 URL 离线时会回退到同一份 `/mobile?relay=1` PWA shell。
- Relay 设备 token 落盘时已经改为哈希存储，旧明文 store 会在写入时迁移。
- Relay health、CLI doctor 和部署 smoke 会暴露/拦截开发默认 admin token。

## 产品原则

### 1. 本地优先执行

电脑端负责：

- 运行 Codex、Claude、Gemini、shell 等 Agent。
- 管理真实 PTY。
- 读写 workspace 文件。
- 保存供应商 API Key、auth.json 等敏感认证文件。
- 判断高风险操作是否允许执行。

Relay 负责：

- 手机和电脑配对。
- 设备 token 鉴权。
- HTTP / WebSocket 转发。
- 在线状态和断线提示。
- 临时文件传输。
- 设备撤销和连接管理。

### 2. 手机优先控制

手机端不是缩小版电脑页面，而应该是适合触屏的控制端：

- 清晰查看 workspace 和 agent。
- 点进 agent 后可以直接控制终端。
- 手机需要稳定输入、回车、退格、Ctrl+C、Esc、Tab。
- 支持上传图片、下载电脑文件。
- 支持断线重连、设备切换、接管状态提示。

### 3. 终端接管要明确

真实 PTY 不能同时完美适配电脑宽屏和手机窄屏。因此：

- 默认电脑拥有 PTY 尺寸。
- 手机需要控制时显式接管。
- 手机接管后，电脑端显示“手机正在接管”。
- 电脑可以一键重新接管。
- 被动查看端不能偷偷 resize 真实 PTY。

### 4. 早期共享可以简单，正式使用必须隔离

给朋友临时体验时，Basic Auth 或单独测试账号可以接受。

正式面向用户时需要：

- 独立账号。
- 独立设备 token。
- workspace 隔离。
- 设备撤销。
- 高风险操作记录。

## 阶段 0：稳定当前开发版

目标：让当前本地和服务器开发方式足够稳定，可以继续日常开发。

交付：

- 本地能启动 Yive runtime 和手机页面。
- 服务器能启动 Relay。
- 电脑能通过 `yive connect` 连接 Relay。
- 手机能通过 `/mobile?relay=1` 配对并操作。
- 终端接管不会破坏电脑端显示。
- Relay 重启后设备 token 不丢。
- Relay pairing store 不明文保存可复用的手机 device token。
- Relay doctor 和部署 smoke 能发现开发默认 admin token。
- CLI 可以查看和撤销配对设备。

验收：

- `pnpm check` 通过。
- Relay / mobile / terminal 相关测试通过。
- 真机手机可以完成：配对、打开 workspace、打开 agent、接管终端、输入命令、释放或电脑重新接管。

## 阶段 1：公网 Relay MVP

目标：手机不在局域网内，也能控制本地电脑 Agent。

交付：

- VPS 上运行生产 Relay。
- HTTPS / WSS 反向代理。
- 配对 token 持久化到固定数据目录。
- CLI 支持：
  - 启动 Relay。
  - 电脑连接 Relay。
  - 查看已配对设备。
  - 撤销设备。
- 手机端支持：
  - 输入服务器地址。
  - 认领配对 token。
  - 保存 device token。
  - 自动重连。
- 手机端清楚显示：
  - 没有电脑在线。
  - 电脑在线。
  - 终端不可用。
  - 电脑断开。
  - token 已失效。

验收：

- 手机用移动网络可以控制家里或办公室电脑上的 Yive。
- Relay 重启后手机不用重新配对。
- 电脑断开时，手机终端显示明确原因。
- 被撤销的手机不能继续连接。

## 阶段 2：终端接管和手机输入稳定化

目标：手机上使用原始终端足够稳定，可以真实开发。

交付：

- 手机点进 agent 默认进入可接管的原始终端。
- 手机接管后电脑端显示接管提示。
- 电脑端可以重新接管。
- 电脑重新接管后，手机进入查看或等待重新接管状态。
- 手机输入稳定支持：
  - 普通文本。
  - Enter。
  - Backspace。
  - Ctrl+C。
  - Esc。
  - Tab。
  - 粘贴文本。
  - 中文输入法。
- 终端渲染避免：
  - 大段空白。
  - 光标和输入错位。
  - 宽度不断收窄。
  - 隐藏面板触发错误 resize。

验收：

- 自动测试覆盖 active / passive / takeover。
- 真机测试长输出、思考动画、行尾输入、退格、刷新恢复。
- 刷新前后的终端状态一致，不靠刷新掩盖 live output 问题。

## 阶段 3：文件和图片传输

目标：手机和电脑可以互传文件，不依赖“本地路径粘贴”这种云端不可用的方式。

交付：

- 手机上传图片，通过 Relay 送到本地电脑 runtime。
- 电脑 runtime 把图片保存到本地附件目录。
- Agent 收到稳定附件引用，而不是服务器路径或手机路径。
- 本地模式和 Relay 模式使用同一套附件语义。
- 电脑 workspace 文件可以发送给手机下载。
- 第一批文件类型：
  - 图片：png、jpg、jpeg、webp。
  - 交换文件：md、mp4、pdf、zip、log。
- 文件是临时交换项，默认 24 小时过期，并且可以手动清理或撤销。

验收：

- 本地 LAN 上传图片可用。
- 公网 Relay 上传图片可用。
- 手机可以下载电脑发送的 mp4 / md / pdf / zip / log 文件。
- terminal prompt、mobile DOM、日志里不泄露 token、base64、大段本地路径或 registry path。

## 阶段 4：服务器运维化

目标：服务器上的 Relay 可以长期稳定运行和更新。

交付：

- `systemd` 服务。
- 日志查看命令。
- 升级流程：
  - `git pull`
  - `pnpm install`
  - `pnpm build`
  - 重启服务
- 目录分离：
  - 生产 runtime。
  - 开发 workspace。
  - Relay 状态。
  - 临时文件。
- pairing store 和配置备份。
- 基础健康状态：
  - 服务是否在线。
  - 连接了几台电脑。
  - 连接了几台手机。
  - 最近错误。

验收：

- 服务器重启后 Relay 自动恢复。
- 升级不会丢失已配对设备。
- 部署失败时可以回滚到上一个 commit。

## 阶段 5：账号和权限隔离

目标：从“给朋友一个密码体验”升级到真正可管理的多用户访问。

交付：

- 用户账号。
- 每个用户有自己的电脑设备。
- 每个用户有自己的手机设备。
- workspace 可见性隔离。
- 邀请朋友或测试用户的流程。
- UI 里可以撤销设备。
- 权限模型：
  - 仅查看。
  - 控制终端。
  - 文件传输。
  - workspace 管理。
- 高风险操作审计：
  - terminal input。
  - stop / restart。
  - 文件传输。
  - 设备撤销。

验收：

- 测试用户不能看到主账号的私有 workspace。
- 撤销测试用户后，HTTP 和 WebSocket 都断开。
- 共享链接不能绕过配对和权限。

## 阶段 6：PWA 体验打磨

目标：在做原生 App 前，让 Web 版已经像一个可安装的手机应用。

交付：

- 全站 HTTPS。
- PWA 可添加到主屏幕。
- Chromium 和 iOS/Safari 都有可发现的安装入口。
- 正确的应用名、图标、启动地址。
- 带 `desktop_id` 的手机直连 URL 离线时仍能加载 PWA shell 并显示连接状态。
- 正确的手机/桌面安装截图。
- 离线/断线状态页。
- 记住服务器和设备选择。
- 390px / 430px 手机宽度布局稳定。
- 上传体验：
  - 相册/文件选择。
  - 上传进度。
  - 成功/失败提示。
- 重连体验：
  - 自动重试。
  - 重连中提示。
  - stale terminal 恢复。

验收：

- iOS / Android 都可以添加到主屏幕。
- 从主屏幕打开直接进入远程控制流程。
- 切换 Wi-Fi / 移动网络后能恢复连接。

## 阶段 7：原生 App 原型

目标：验证真正 App 是否明显优于 PWA。

建议技术栈：

- React Native + Expo。
- 尽量复用 TypeScript API 类型。
- 复用 Relay 协议。

交付：

- 登录/配对页面。
- 设备、workspace、agent 列表。
- 终端接管页面。
- 图片和文件选择。
- 手机下载和打开电脑发来的文件。
- 基础推送通知：
  - Agent 需要确认。
  - 任务完成。
  - 电脑断开。

验收：

- App 可以通过公网 Relay 控制真实本地电脑。
- 图片和文件上传体验优于浏览器。
- 推送可以提醒用户处理关键 Agent 事件。

## 阶段 11：本地执行端产品化

目标：把现在的开发者命令行运行方式，收敛成普通用户也能长期运行的本地电脑执行端。

交付：

- Windows / macOS / Linux 本地执行端安装包。
- 后台常驻进程和托盘菜单。
- 开机自启动。
- 本地 runtime 自动升级。
- 本地日志、诊断包和一键复制故障信息。
- 本地 Agent CLI 检测：
  - Codex。
  - Claude。
  - Gemini。
  - shell。
- API Key / auth.json 配置向导。
- 本地 workspace 授权目录管理。
- 本地危险操作确认策略。

验收：

- 用户不需要打开源码仓库，也能启动本地执行端。
- 手机可以看到电脑在线、离线、升级中、需要认证等状态。
- 本地执行端崩溃后能自动恢复，且不会丢失已配对手机。

## 阶段 12：Relay 连接质量和弱网体验

目标：让公网远程控制在移动网络、弱 Wi-Fi、切后台、锁屏恢复后仍然可用。

交付：

- Relay 心跳和延迟显示。
- 自动重连分层：
  - 手机到 Relay。
  - 电脑到 Relay。
  - Relay 到本地 runtime。
  - terminal WebSocket。
- 断线期间的操作保护，避免用户以为命令已经发送。
- 连接恢复后的终端快照恢复。
- 文件上传断点保护或失败重试。
- 连接质量诊断页面。
- Relay 侧连接事件审计。

验收：

- 手机从 Wi-Fi 切到 5G 后可以恢复控制。
- 手机锁屏再打开后状态准确，不需要刷新页面。
- 电脑断网再上线后，手机能明确看到重连结果。

  - 运行测试。

## 阶段 16：PWA 到原生 App 的迁移桥

目标：在正式做原生 App 前，把 Web/PWA 的协议、状态模型和页面结构整理到可复用状态。

交付：

- 抽离 Relay client。
- 抽离 mobile runtime client。
- 移动端协议类型以 `src/shared/types.ts` 为准，包含 `MobileSnapshot`、`MobileEventsServerMessage`、`MobileRuntimeClientContract`、文件交换、transcript 和 dispatch wire 类型。
- 移动端事件解析以 `src/shared/mobile-events.ts` 为准，PWA、Relay client 和后续 Expo / React Native App 不应各自复制 `mobile-snapshot` / `mobile-heartbeat` 判定逻辑。
- 抽离 terminal takeover 状态机。
- 抽离文件传输状态机。
- 移动端 UI 组件边界稳定。
- App 和 PWA 共享 TypeScript 类型。
- 原生 App 技术验证：
  - Expo / React Native。
  - WebSocket。
  - 文件选择。
  - 图片选择。
  - 安全 token 存储。
  - 推送通知。

验收：

- 新建 App 原型时，不需要重写 Relay 协议。
- PWA 和 App 对同一个 Relay 后端行为一致。
- App 原型可以控制真实本地电脑 Agent。

- 多人协作不会导致 PTY resize 和 terminal ownership 混乱。

## 阶段 19：平台化和计费准备

## 阶段 20：长期产品形态

目标：Yive 成为一个“随身开发控制台”，手机只是入口，本地电脑仍然是主要执行和私有数据边界。

长期能力：

- 手机随时接管本地开发 Agent。
- 电脑作为私有执行节点。
- 云 Relay 只负责连接、权限、通知和临时中转。
- Agent 可以跨设备连续工作。
- 用户可以在电脑、手机、平板之间切换控制权。
- 项目文件默认不上传云端。
- 敏感认证默认不离开本地电脑。
- 小团队可以安全共享开发任务。

最终判断标准：

- 用户在外面只拿手机，也能安全地推进本地电脑上的真实开发任务。
- 服务器宕机只影响远程连接，不应该破坏本地 workspace。
- 手机 App 不是桌面网页缩小版，而是为远程开发控制重新设计的入口。

## 阶段 40：Yive 平台最终形态

目标：Yive 成为一个“本地执行、云端连接、手机优先、多 Agent 协作”的远程开发平台。

最终形态：

- 手机 App 是主控制入口。
- 电脑桌面端是私有执行节点。
- Relay 是连接、鉴权、通知和临时中转层。
- Agent 运行在用户授权的本地或私有环境。
- 源码和敏感认证默认不上传官方云。
- 用户可以选择：
  - 局域网模式。
  - 自托管 Relay。
  - 官方托管 Relay。
  - 企业私有化。
- 开发任务可以跨设备、跨 Agent、跨团队流转。
- 文件、终端、审批、通知和任务状态形成闭环。

最终验收：

- 用户只带手机，也能安全推进真实项目开发。
- 本地电脑断开时，云端不会假装任务还在运行。
- 官方云故障不破坏本地 workspace。
- 手机、桌面端、Relay 和 App 都有清晰边界。
- Yive 不只是网页工具，而是一个完整远程开发控制系统。

## 近期优先级

接下来最实际的顺序是：

1. 把当前 Relay / mobile 构建部署到服务器。
2. 用手机公网测试控制本地电脑。
3. 修复真实使用中发现的接管、重连、输入问题。
4. 做电脑文件发送到手机下载。
5. 做 Relay 安全的手机图片上传到本地 Agent。
6. 配 HTTPS 和 PWA 安装体验。
7. 做设备管理 UI。
8. PWA 稳定后再启动原生 App 原型。

## 暂时不做

这些方向有价值，但不应该挡住当前远程控制主线：

- 默认把 Agent 全部跑在云端。
- 一开始就做完整 SaaS 多租户。
- 追求完美的多 viewer 终端重排。
- 把 Relay 做成长期文件网盘。
- 替换现有电脑端 Web UI。
- PWA 没稳定前就先投入原生 App。

## 长期目标完成定义

这个长期目标不能因为某个单点功能完成就算完成。只有下面都满足，才算真正完成：

- 手机 App 或 App-like PWA 可以通过公网控制本地电脑 Yive runtime。
- 真实 Agent 仍然运行在用户自己的电脑上。
- Relay 不需要直接访问用户源码或供应商 API Key。
- 配对、重连、撤销、设备管理可靠。
- 终端接管在真机上稳定。
